## 三、M3 执行要点（Trae 注意）

### 1. LLM 封装（llm.py）
- DeepSeek API（OpenAI 兼容协议），模型 `deepseek-chat`
- **JSON mode + Pydantic 校验**（结构化输出，解析失败重试 1 次）
- temperature 按任务：摘要 0.3 / 金句 0.3 / 大纲 0.2 / 广告识别 0.1
- 超时与重试：网络错误重试 2 次，指数退避

### 2. 分段输入（关键——避免超上下文）
- 转写全文可能几万字，**按段落分批送入 LLM**，再合并结果
- 摘要：分块摘要 → 合并成最终 300 字内「人话摘要」
- 大纲：先分块提取章节候选 → 合并去重 → 排序（带时间戳）
- 金句：分块提取候选 → 合并去重 → 按「金句质量」排序取 3-8 条
- 广告识别：**段落级**（直接逐段判断 is_ad），不进全文

### 3. 金句可溯源（硬性要求）
- 每条金句的 `{text, start_ts, end_ts}` 必须对应转写原文（时间戳能找到）
- **校验**：生成后检查金句 text 是否能在对应段落中找到（子串匹配，模糊容忍）——找不到则丢弃该金句并记录

### 4. 广告识别（人在环上的基础）
- 返回 `[{para_id, is_ad, reason}]`——段落级标注
- 识别特征：赞助口播（「本期由XX赞助」「感谢XX」）、推广话术（「点击链接」「优惠码」）、硬广段落
- 只标记「明确是广告」的段落（宁可漏，不可误杀——误杀用户内容比漏广告更伤）

### 5. 异步与进度
- 4 项加工作为转写完成后的**后续任务**（transcribe 成功后自动触发，或提供独立 API 手动触发）
- 进度可查（复用 M2 的 transcript_progress 模式，或独立加工状态字段）

### 6. 测试要求
- LLM mock（注入 mock 客户端）：4 项任务输出结构正确、金句可溯源校验生效、广告标记段落级
- 真实验证：用 1 集真实转写（M2 已有声动早咖啡数据）跑通 4 项，人工检查摘要/金句质量
